# Git 提交规范

本项目采用 [约定式提交（Conventional Commits）](https://www.conventionalcommits.org/) 标准。

## 提交消息结构

```
<type>(<scope>): <description>

[正文]

[尾部]
```

> 提交信息（标题、正文、尾部）中不写入 `FR-xxx`、`SC-xxx`、`USxx` 之类的任务编号——这类编号只在当次 spec 或会话内有效，不进入提交历史。

## 1. 标题（必填）

格式：`<type>(<scope>): <description>`

示例：`feat(transfer): 新增传输进度百分比显示`

### 类型（type）

| 类型 | 用途 |
|------|------|
| `feat` | 新功能 |
| `fix` | 修复缺陷 |
| `docs` | 文档变更 |
| `style` | 代码样式调整（不影响功能，如格式化、空格） |
| `refactor` | 代码重构（既非新功能也非修复） |
| `perf` | 性能优化 |
| `test` | 测试相关（新增、修改、补充用例） |
| `build` | 构建系统或外部依赖变更（Rust 编译脚本、ohpm 依赖等） |
| `ci` | CI/CD 配置变更 |
| `chore` | 其他不涉及源码的杂项（.gitignore、IDE 配置等） |
| `release` | 版本发布（升级应用版本号，通常配合 release 构建与 v* 标签） |
| `revert` | 回退之前的提交 |

> **注意**：类型必须使用上述小写关键字，不使用自定义类型。

### 范围（scope）

可选，用括号包裹，表示变更涉及的模块或区域。推荐使用以下范围：

| 范围 | 说明 |
|------|------|
| `transfer` | 文件传输流程（发送/接收/进度/取消） |
| `send` | 发送侧流程 |
| `recv` | 接收侧流程 |
| `mta` | 互传联盟（MTA）收发流程 |
| `server` | 本地服务器（启停/配置） |
| `web` | Web 分享页面 |
| `discovery` | 设备发现与组播 |
| `settings` | 设置页面与偏好存储 |
| `native` | Rust HAR 层（localsend_ohrs） |
| `bridge` | NativeBridge 桥接层 |
| `ui` | UI 布局/组件/样式 |
| `log` | 日志模块 |
| `build` | 构建脚本与工具链 |

范围不是封闭列表——当变更集中在某个具体文件或小区域时，也可以用文件名或简短标识，如 `bridge`、`log`。如果变更跨多个模块，可省略范围。

### 描述（description）

- 以动词开头，简明扼要说明「做了什么」
- 动词描述**内容的变化**（新增 / 调整 / 移除 / 修复），少用只表动作的词（同步、更新）
- 说**规则或行为**，不点明载体（文件名、目录、标记区块）——`git log --oneline` 只显示标题，
  改了哪个文件 diff 自明
- 可用逗号从句把关键要求写进标题（"调整 X，要求 Y"），单行扫读即可见约束
- 不超过 50 个字符
- 使用中文
- 不加句号

| ✅ 正确 | ❌ 错误 |
|---------|---------|
| `feat(transfer): 新增传输进度百分比显示` | `feat(transfer): 新增了传输进度百分比显示的功能。` |
| `fix(discovery): 修复更改端口时无法发现设备` | `fix: bug fix` |
| `refactor(log): 调整日志级别，CRUD 细节降为 debug` | `refactor: 一些重构` |
| `docs: 调整日志拉取规则，要求按包名与设备过滤` | `docs: 同步鸿蒙规则区块的日志过滤要求` |

## 2. 正文（可选）

- 详细说明变更的**背景、原因和结果**——为什么改、改了什么、有什么影响
- 推荐「问题/原因」+「效果/收益」两条式：先说为什么要改，再说对使用者的好处；
  收益写可感知的影响（噪声、误判、耗时、风险），不写技术细节
- 用概括表述，不罗列参数名或文件清单（"按包名和设备过滤"即可，不必列
  `--bundle-name` / `--device`）——那是 diff 的职责
- 写给**半年后查历史的人**：回答"什么变了、为什么变"，不回答"我是怎么改的"
- 描述对象必须**在本仓库内**（文件、行为、约定）。提交信息会随仓库分发、被 CI 与他人阅读，指向本机专有资产（其他本地仓库、绝对路径、家目录）的指针在他们那里无法解析，而文件位置 diff 自明
- 单一变更可以只写标题，不写正文
- 每行不超过 72 个字符
- 使用中文
- 与标题空一行
- 多项内容用 `-` 列表，便于阅读
- 列表项必须以 `- ` 顶格开头（`-` 前不能有空格或 tab）
- 列表项过长时可在下一行用 4 个空格缩进续行

### 不该写进正文的内容

| 类型 | 例子 | 为什么 |
|------|------|--------|
| 操作手段 | "重新 deploy 区块"、"用 sed 降级标题" | 手段在 diff 里，半年后可能就不这么改了 |
| 自证与校验 | "区块外无改动"、"与源文件逐字一致"、"已按 --help 核对" | 提交本就该只有预期改动；验证结论属于 PR 描述或对话 |
| 重复标题 | 首条与标题同义复述 | 占位不增信息，首条该补标题没说的理由或影响 |
| 文件台账 | "README 那一行也同步改了" | diff 自明，除非改动影响使用方式 |
| 仓库外引用 | "同步 hmos-opencode-config 的规则源" | 别人 clone 后无此仓库，指针失效 |

生成物与同步来源这类持久信息（"该文件由哪个脚本生成、勿手工编辑"）写进**本仓库文档**，不写进提交信息——
提交信息只说内容变成了什么。

示例：

```
fix(transfer): 修复小文件传输时进度条提前到 100%

- 文件总大小在 SendContent 初始化时缓存，避免每次 UI 刷新同步调用 statSync
- 进度回调改为基于已传输字节数而非文件数计算
```

```
❌ docs: 同步鸿蒙规则区块的日志过滤要求

- 重新 deploy HMOS-DEV-RULES 区块，区块外项目自有内容无改动
- 区块新增取日志过滤要求（--bundle-name / --device），禁止裸跑 devecocli log 拉全量

✅ docs: 调整日志拉取规则，要求按包名与设备过滤

- 设备日志刷新快，系统日志几秒内就会把应用日志冲掉
- 增加包名和设备等过滤要求，可以极大程度减少日志噪声
```

```
❌ docs: 调整 hmos-opencode-config 规则区块的日志过滤要求

- 重新 deploy 区块，同步配置包仓库的规则源

✅ docs: 调整鸿蒙规则区块的日志过滤要求

- 新增取日志过滤要求（--bundle-name / --device），禁止裸跑 devecocli log 拉全量日志
```

| ✅ 正确 | ❌ 错误 |
|---------|---------|
| `- 列表项文字`（顶格） | `  - 列表项文字`（`-` 前有空格） |
| `    `（4 空格缩进续行） | `    - 列表项文字`（缩进的列表项） |

## 3. 尾部（可选）

- 关联 issue：`Closes #123`、`Fixes #456`
- 破坏性变更：以 `BREAKING CHANGE:` 开头，或标题类型后加 `!`
- 与正文空一行

示例：

```
refactor(native)!: 重构 Rust NAPI 层接口

将轮询机制迁移到事件回调模式，桥接层拆分为多模块。

BREAKING CHANGE: NativeBridge 的 onDiscovery 回调签名变更，调用方需适配新参数结构
```

`!` 是 `BREAKING CHANGE` 的简写——标题中加 `!` 等同于尾部写 `BREAKING CHANGE:`，两者选其一即可。

## 完整示例

### 简单提交（仅标题）

```
fix(settings): 修复恢复默认设置缺少确认对话框
```

### 带正文的提交

```
feat(log): 统一日志系统 — Logger 模块封装 hilog + Debug 开关

- 封装 Logger 模块，统一调用 hilog 的接口
- 通过 isDebug 开关控制日志级别
- 替换全项目散落的 hilog 直接调用
    包括 TransferViewModel、SendRepository 等 12 处
```

### 破坏性变更

```
refactor(bridge)!: 桥接层拆分为多模块

将单一 NativeBridge 拆分为 DiscoveryBridge、TransferBridge、ServerBridge。

BREAKING CHANGE: 原 NativeBridge 类已移除，需按功能引入对应 Bridge
Closes #12
```

## 自动校验

项目通过 Lefthook + commitlint 自动校验提交信息格式，不符合规范会被拦截。

- 配置文件：`commitlint.config.js`（规则与本文档一致）
- 校验工具：commitlint + @commitlint/config-conventional
- Hook 管理：lefthook（`lefthook.yml`）

被拦截时，按规范修改提交信息后重新提交即可。紧急情况可绕过：`LEFTHOOK=0 git commit`。

## 常见问题

**Q：一个提交包含多种类型怎么写？**
A：按主要目的选类型。重构中顺带修了个 typo → 用 `refactor`；修 bug 时发现需要新增辅助函数 → 仍用 `fix`。

**Q：scope 怎么选？**
A：优先用上面推荐的模块范围。如果改动集中在一个文件或小组件，用文件名也行。跨模块改动省略 scope。

**Q：描述用中文还是英文？**
A：中文。与项目代码注释规范保持一致。

**Q：正文写多细？哪些内容根本不该写？**
A：写"什么变了、为什么变"，不写"我怎么改的"和"我验证过了"。操作手段、自证校验、重复标题、文件台账、
仓库外引用这五类不进正文，完整反例见「§2 不该写进正文的内容」。单一变更只写标题即可。
