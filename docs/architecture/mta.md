# MTA（互传联盟）集成

> MTA 发现、发送/接收编排、对外身份与模拟品牌、接收历史与文件保真的实现细节。
>
> 主文档 `docs/ARCHITECTURE.md` §4.2 / §8.2 保留概述；统一会话建模见 `session-engine.md` 与 `repositories.md`；
> 协议层细节（BLE 握手、ECDH、WiFi Direct 时序）见 `docs/mta/MTA_PROTOCOL.md`。

## 1. 架构定位

`entry/src/main/ets/service/repository/MtaRepository.ets` 为应用级 MTA 运行时：

- 持有仅用于发现的 `MtaBleClient` 实例与 MTA 接收服务单例
- 提供发现扫描、接收服务启停、收发互斥、接收命令门面与对外身份刷新（昵称或「模拟品牌」变更时重广播）
- 变化经 `AppCore.notifyChange` 通知 UI
- AppService 门面再导出其全部对外函数，供发送页、设置页与应用生命周期调用

## 2. 发现与设备展示

### 2.1 BLE 发现扫描

- `MtaRepository` 在发送页可见期间保持 BLE 发现扫描（均衡功耗扫描模式）；切走 Tab、推入子页面或应用退后台即停止
- 发现意图拆分为「可见性期望」与「发送暂停」两个独立意图：发送暂停只临时挂起扫描，不抹除可见性期望，
  发送结束（成功/失败/取消）后按可见性期望显式恢复发现；用户离开页面或关闭总开关仍清除两者
- 蓝牙开关状态经三态（已开启 / 已关闭 / 不可确定）判定：查询异常与「开启中/关闭中」等中间态归为不可确定，
  不可确定不按关闭处理、不清空也不隐藏互传分组；仅「确认关闭」（经去抖确认）才停止扫描、清空列表并复位接收服务，
  蓝牙重新开启后按需自动恢复扫描与接收服务（跳过失败冷却）
- 剔除策略以「扫描健康」为前置：仅扫描中且最近一次有新发现结果处于停顿阈值内时才剔除超时条目（30 秒未见即离线），
  扫描不健康一律跳过剔除且不改变列表；剔除动作按触发场景分级记录日志
- 用户主动刷新（点击刷新）：不整列清空（避免列表闪空），改为重置上报去重使在线设备在确认窗口（3 秒）内
  重新上报而保留，窗口结束仍未被再次发现的条目按离线即时剔除（无需等满存活期 TTL）；确认窗口判定同样以
  「扫描健康」为前置
- 设备身份跨回调稳定：主广播段与扫描响应段可能分次到达（或某次缺段），扫描端按广播地址累积已见的设备 ID
  两段/品牌/名称/5GHz，跨回调拼接出完整设备 ID 并沿用已见值，避免同一设备因分次到达被当作新设备
  （列表出现多个条目、品牌徽标在条目间跳变）
- 扫描静默停顿检测：处于扫描中但距最近一次发现结果达到停顿阈值（不小于设备存活期 TTL）即判为疑似停顿，
  记录诊断并触发一次扫描恢复，恢复确认前继续跳过剔除，避免既有条目被逐步剔光
- 起扫自愈重试：页面仍期望扫描却未在扫描时（起扫失败进入失败冷却、蓝牙/权限瞬时不可用、可见性事件
  时序未触发等），按固定间隔重试起扫，直至起扫成功或不再期望扫描；蓝牙确认关闭时停止重试，交由
  蓝牙状态事件在开启后恢复。避免设备列表长期不刷新、只能靠用户手动刷新或切页才恢复
- 起扫前置门控：蓝牙权限未授予时不发起注定失败的 BLE 扫描、也不进入失败冷却，改由自愈重试在授权后
  起扫。启动时「权限申请串行链」（通知权限 → 蓝牙权限，含系统弹窗与用户交互）排在 UI 首帧扫描之后，
  二者存在竞态，故不能依赖权限已就绪
- 互传分组所有「非空→空」的清空路径统一经诊断出口记录（原因分类 + 清空前条目数 + 触发场景 + 时刻，
  同类事件节流去重），原因覆盖蓝牙真实关闭 / 超时剔除 / 扫描停顿 / 未知等，使每一次清空均可被定位

### 2.2 统一设备集与条目渲染

- 发现的互传联盟设备经 `DiscoveredDevice` 统一形状（`protocol = 'mta'`）合并进统一设备集，且不参与 LocalSend 收藏；`discoveredDevices` 仍仅含 LocalSend，未污染既有发现/收藏逻辑
- 条目以对端手机品牌图标与品牌徽标替代设备类型图标与 IP 短码（图标按广播品牌标识经 `MtaBrandRegistry` 解析，无专属图标的品牌与未知品牌回退默认兜底）
- 互传对端身份取「对端发送者 ID」（`senderIdHex`，跨会话对观测厂商稳定）：发现列表去重键、列表条目复用键、
  会话注册表「同设备」判定与设备卡标识区四处同一口径；`senderIdHex` 缺失时回退 BLE 地址。会话注册表匹配
  按 IP → 稳定标识 → 昵称的回退顺序，故同名不同机不再互相取代、同机改名/重连不再残留旧条目
- 本机 MTA 设备 ID **持久化**（首次生成 16 字节随机后写入 Preferences，跨会话稳定，对齐厂商行为；
  接收广播与发送侧标识共用同一取值），使对端把本机在各会话间视为同一台设备。是否跨会话稳定由各实现
  自行选择（真机实测小米稳定、第三方 EasyShare 不稳定）

### 2.3 附近设备区域与来源标签

发送页「附近设备」区域由设备来源注册表通用渲染（`SendTargetZone`）：

- `SendViewModel` 经 `model/SendDeviceGrouping.ets` 纯函数把统一设备集拆为局域网/互传两组展示数据源
- 来源标签仅在本次发送页会话曾发现该来源设备时出现（互传侧经 `hasSeenMtaDevice` 会话内保持；来源数小于 2 时不展示标签）
- 选中来源按**下标**持有（而非来源键）：官方分段标签组件按索引持有选中态，若父级按来源键存选中，
  则「可见来源集合」增长/重排后同一索引会指向不同来源（冷启动常见：先发现互传设备→集合只有 `[互传]`，
  其后局域网设备出现→集合变为 `[LocalSend, 互传]`），出现「页签停在一个来源、列表却按另一个来源取数」
  的不一致。故选中态统一下标持有、由下标派生来源，两侧由构造保持一致
- 互传设备数归零时展示互传专属空态，空态文案由来源描述符提供：引导开启本机蓝牙与 WLAN（无需连接网络）并确认对端在附近且已开启分享
- 收藏区块仅在局域网来源下渲染

### 2.4 连接警告横幅

发送页连接警告横幅（与网络警告同款式）按优先级只显示一条：

- WLAN 关闭且局域网不可用：与既有「未连接局域网」提示合并（互传发现依赖蓝牙、传输依赖 WLAN，有线局域网不可替代，此时两者是同一件事）
- WLAN 关闭但局域网可用（如已接网线）：只提示互传需要 WLAN（设备可被发现但无法传输）
- 蓝牙与 WLAN 均未开启：显示合并提示（互传口径）
- 仅蓝牙关闭：提示开启蓝牙
- 互传相关提示以「互传联盟接收」开关为前提（关闭时接收端不广播）
- 互传相关提示受设置「互传连接提醒」（`mtaConnectionWarnings`，默认开启）控制，关闭后不再显示互传相关警告、仅保留 LocalSend 自身的局域网警告
- 三方应用无法主动开启 WLAN（`wifiManager.enableWifi` 仅系统应用可用），故仅作提示引导

## 3. 发送编排

- 点击 MTA 设备经 `SendContent` 按 `protocol` 分流到 MTA 发送编排
- 发送前读取对端 `DeviceInfo` 后判定对端是否忙（`state` 非就绪值，判定依据见协议文档 §1.4）：判忙即以「对端设备正忙，请稍后重试」结束本次发送，
  不建组、不起服、不写回凭据，忙原因码仅入诊断日志；不自动重试，对端就绪时流程与结果不变
- `MtaSendAdapter` 承接 `MtaSendService` 生命周期、收发互斥（发送前暂停发现扫描并暂停接收服务，会话终态后按开关与可见性期望恢复）
  与取消/重试，并把会话登记到统一注册表（进度与结果经任务与通用详情页呈现，不再有 MTA 专用传输页）
- 建链编排时序（缩短「点击→对端弹窗」）：
  - 点击后并行启动与对端无关的本地准备：本地传输服务（绑定 `0.0.0.0`、由系统分配端口，
    含直读 fd 打开与预览生成）立即推进，并与接收对外服务收尾并行；建组（有界清理旧组→建组→
    以群组身份校验就绪）在接收外设释放后启动，与 BLE 凭据交换（地址获取/连接/读取/写回）并行
  - 「写回凭据」只依赖「组就绪 + 对端信息可写 + 端口已知」；预览生成与句柄打开不阻塞写回
  - 对端地址「先用后扫」：优先使用点击时记录的广播地址直连，仅在实际连接失败后才按 `senderId` 重扫回退
  - 组网就绪以 P2P 连接事件为主判据（事件缺失时以短步长轮询兜底），并以**群组身份**为准：就绪组名须等于
    本次请求创建的组名，不匹配（含上一会话尚未拆除的残留组）即视为未就绪，在候选预算内有界重试，绝不采用
    残留群组的无线凭据
  - 建组前对上一会话残留群组做有界处置（确认其消失，超时未消失不阻断建组），失败由群组身份校验兜底
  - 写回后复读对端公开信息为非阻塞诊断，与「等待对端入组」并行采集，仅用于收束归因
  - 收发互斥为「并行切换」：发起发送不等待接收对外服务完全停用，本地准备与接收外设收尾并行推进；
    启动发送伴随外设前才等待接收服务释放，复用/切换失败按既有路径降级且不劣化
  - 建链阶段耗时统一口径：以用户点击为起点，记录「点击→写回凭据」「点击→对端接入」与各阶段相对耗时
- 已有 MTA 发送进行中时提示设备忙并忽略（判定以统一会话注册表的活跃会话为唯一事实源；会话一进入终态
  （含用户取消）即视为空闲，不等待服务侧资源释放，避免取消后仍被判忙）
- 与来源无关的发送方式入口（网页分享 / 网页接收 / 指定 IP 分享）经方式注册表在目标区标题行的图标菜单中按「网页」与「其它方式」分组渲染
- 发送预览：顶层 `mimeType` 按三档口径聚合（`MimeUtils.aggregateMtaMimeType`）——单文件用真实 MIME、
  多文件同大类用大类通配、跨大类用全通配；仅当全部文件都是媒体（图片/视频）时，取首个文件生成等比缩放入
  240×320 框内的 JPEG（`ImageThumbnailUtil.writeSendThumbnail`，暂存于 `cacheDir/send/`），随 `sendRequest`
  声明 `thumbnail` 与 `thumbnail_width`/`thumbnail_height`，由 Rust `GET /thumbnail?taskId=` 定长返回；
  混类型不声明预览，生成失败按不提供降级，均不阻断发送
- 会话收尾：Rust 发送端所有收尾路径（成功/取消/拒绝/失败/超时）统一经「会话终止」过程——在确保
  结束类指示（结果回执 / 取消状态）已被对端读取后，以**连接终止**（**不发 WebSocket 关闭帧**）结束
  会话；成功路径仅在收到对端终态并回送确认之后才终止。对端（小米使用的 OkHttp WebSocket 客户端）的
  「关闭完成」回调仅在客户端自身发起关闭时触发、收到服务端关闭帧后即停止读取，故服务端发关闭帧只会
  触发其空实现的「关闭中」回调；终止连接使对端进入其可处理的「连接失败终止」路径并完成自身收尾。
  成功终态达成即停止发送服务器（断开 WS 连接）并释放无线资源，不延迟收尾，使对端尽快清忙、连续发送
  不被「对端忙」拦下
- 对端忙判定：读取对端 `DeviceInfo` 后 `state` 非就绪值即判忙，在建组/起服/写凭据前收束；对「明确冲突」
  （`reason` 为镜像/热点占用）直接收束，对其余（含未知原因 0，覆盖上一会话收尾期内、尤其本机在对端弹出
  确认前取消留下的短暂残留）进入「等待对端就绪」阶段并**按 4 秒间隔**复读（对端读到未就绪时其自身已先等
  最多 4000ms 才应答，间隔与之对齐；总窗约 12 秒），就绪即继续、窗口用尽才收束
- 群主地址（`P2pInfo.mac`）：取本机 P2P 网卡硬件地址（Native 读取），对外统一小写；对端入组后校验
  `owner.deviceAddress == mac`，不符即未识别群主并中止（可能滞留忙态）。`ownerInfo.deviceAddress` 对
  三方应用为随机值，**不下发**——读取失败一律按建组失败收束，不做随机地址降级
- `P2pInfo.id` 写本机 MTA 设备 ID（持久化值，与中兴 `getDeviceId()` 同义；见 §2.1 的身份口径）；
  WS `sendRequest` 的 `taskId`/`id` 则是任务 ID——两个同名字段语义不同，取值分别对应设备身份与本次任务
- 发送条目尺寸来源：`sendRequest` 声明的各条目尺寸与总尺寸取自条目**已打开句柄**的属性
  （`statSync(fd)`），与将发送字节同源；Rust 流式写出按实际读取字节产出载荷，声明尺寸不符时仅记诊断
  而不截断载荷

## 4. 接收流程

- 应用进入前台时按「互传联盟接收」设置（默认开启）自动启动 MTA 接收服务（BLE 广播 + GATT Server），进入后台停止
- 收到互传联盟设备传输请求时经 `MtaReceiveAdapter` 登记为统一注册表的待确认会话，在任务确认/拒绝（应用在后台时另发提示通知）
- 接收确认阶段的对端图片预览：请求携带缩略图标识时，先在有界预算（`THUMBNAIL_PREFETCH_BUDGET_MS`）内预取，超预算即放行、不拖延确认弹窗；
  预取命中则待确认会话创建时即携带预览，未命中则由后台拉取完成后经会话回填，快路径与慢路径结果一致；
  写回以「会话仍活跃且仍持有该请求」为守卫，用户决策、会话复位或请求被取代后不再回填，避免过期预览污染会话
- 请求接受后下载解压落盘到既有接收目录并写入接收历史
- 建链编排时序（缩短「对端发起→本机弹窗」）：
  - 收到对端凭据后，WS 建立前的网络汇总类查询改为并行诊断，不阻塞首次连接探测
  - 会话收尾复用优先：对外身份（昵称/模拟品牌）未变且广播/GATT 仍完整时复用既有服务与密钥，
    身份变化或复用失败回退完整重建，避免连续接收的固定重建开销
  - 接收对外服务的预热/复用受开关与应用生命周期约束：应用退后台或互传开关关闭时显式停止并抑制复用，
    不后台常驻；服务重新启动时解除抑制
  - 建链阶段耗时统一口径：以收到对端凭据为起点，记录「收凭据→本机弹窗」与各阶段相对耗时
- MTA 发送与接收经 `MtaRepository` 互斥：发起发送前暂停发现扫描与接收服务，发送结束（完成/失败/取消）后
  按开关与可见性期望恢复两者

## 5. 接收历史与 MIME

- MTA 接收历史按文件扩展名解析真实 MIME 写入（不再统一记通用二进制类型）
- 该真实类型同时作为「保存到相册」的媒体筛选依据（待保存媒体经 `MtaReceiveAdapter.getGalleryMediaFiles` 接入通用详情页的相册保存入口，见主文档 §4.6）
- **文本接收**：用户接受文本时先把文本写入接收目录（`Download/<包名>/`，重名自动加序号、与普通文件同规则），成功后再回执与回送成功状态；
  写入失败按既有失败语义处理，不谎报成功。接收历史以单一文本条目记**真实路径**与元数据（不写入正文），详情页与文件历史据此读取文件内容
- **文本发送**：互传发送的文本文件写入应用**私有持久目录**下的发送文本目录 `filesDir/text_send/`（路径统一由 `SendRepository.sendTextDir` 提供，
  只在用户主动「清除任务历史」时被清空），对端可见条目名仍为 `sharedText.txt`（协议行为不变）；发送会话携带该文本文件的本地路径，供详情页按路径预览内容

## 6. 对外身份与模拟品牌

MTA 对外身份中的品牌取自设置项「模拟品牌」（`model/mta/MtaBrandRegistry.ets` 为品牌标识 ↔ 名称的单一事实源，默认第三方）。

### 6.1 品牌清单

- 可模拟清单收敛为小米 / OPPO / vivo / 荣耀 / 一加 / 真我 / 三星 / 魅族 8 个主流品牌 + 默认「第三方」
- 用于扫描识别对方设备的品牌标识映射保持完整、不随该清单缩减

### 6.2 协议字段

- 接收端 BLE 主广播 serviceData UUID 的品牌字节按所选品牌生成（默认第三方时等于既有常量）
- 发送端 Rust 服务器配置与 `sendRequest` 载荷携带可选的 `senderBrandId`/`senderBrand`（默认第三方时不序列化、对老对端零影响；`senderBrand` 始终为不随语言变化的规范英文名）
- 品牌变更经 `MtaRepository.refreshMtaReceiveIdentity()` 触发重广播，接收服务未运行时为空操作

### 6.3 生效范围

- 模拟品牌仅对部分厂商生效：厂商扫描端（小米/中兴等）读合并扫描记录固定偏移识别品牌，
  HarmonyOS 广播栈的 AD 编码顺序使品牌字节无法落在厂商期望的偏移上，厂商真机 UI 不识别
  本应用广播的品牌；对按 serviceData UUID 结构化解析的扫描端（本应用自身、CatShare/
  EasyShare 等第三方实现）仍生效
- 互传收发功能不受影响：发现走 serviceUuid 过滤、连接走 GATT、传输走 WS，均不依赖该偏移
  （协议层证据与已排除的替代路径见 `../mta/MTA_PROTOCOL.md` §12.5）

### 6.4 本地化显示

- 设置页显示名随应用语言本地化（`brand_name_<key>` 字符串资源：`base` 英文、`zh_Hans` 简体、`zh_Hant` 繁体，中文下有通用中文名的品牌显示中文名），不影响协议字段与收发界面徽标

## 7. 文件信息保真

文件信息保真覆盖两条链路（源文件修改时间的采集与还原）：

- 局域网发送：暂存前采集源文件修改时间随发送文件 JSON 传入（Rust 桥接填充上传 DTO 的 `metadata.modified`，接收端由核心落盘后应用）
- MTA 发送：发送端直读源文件 fd（每文件一个读取入口，文本条目写入 `filesDir/text_send/` 的文件按路径读取）；
  条目尺寸与修改时间取自该**已打开句柄**的属性（`statSync(fd)`，与将发送字节同源），并把源修改时间写入
  ZIP 条目时间；接收端解压落盘后按条目时间还原、无效时保持落盘时刻（MTA 协议载荷无时间字段，ZIP 条目时间是唯一可承载位）
